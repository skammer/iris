## Дефекты

- [x] **F01 / P1 — shell approval.** `find -exec` выполняет произвольную команду, `sort -o` пишет файл без approval. Ограничить автоматические разрешения безопасными аргументами; сохранить явные пользовательские правила. Регрессии: вложенный executable, запись, обычное чтение.
- [x] **F02 / P1 — credentials при redirect.** HTTP повторяет Authorization/Cookie на другом origin. Удалять чувствительные заголовки при смене origin; проверять также порт и схему.
- [x] **F03 / P1 — cancellation race.** Отмена освобождает сессию до завершения worker; старый финал удаляет новый stream. Сохранить владение сессией до завершения, проверять request-id. Регрессия: cancel → следующий запрос → позднее событие.
- [x] **F04 / P1 — зависшая очередь.** Ошибка event sink после установки active оставляет запрос без worker/result. Разделить изменение состояния и уведомление; гарантировать завершение при отказе executor.
- [x] **F05 / P1 — потеря сохранённого ответа.** Persistence subscriber проглатывает ошибку и публикует успешный message-end. Обязательная persistence должна прерывать успешное завершение; UI callbacks остаются необязательными.
- [x] **F06 / P2 — неверный rollback памяти.** Ошибка audit event после applied откатывает файл, оставляя applied в БД. Исправить границу фиксации/отката; проверить ошибку audit и ошибку фиксации статуса.
- [x] **F07 / P2 — stdout/SIGPIPE.** Reader закрывает pipe на лимите; команда завершается 141. Дочитывать и отбрасывать избыток, возвращать признак усечения, освобождать process/streams при ошибке.
- [x] **F08 / P2 — невидимые потери broker.** Sliding buffer сохраняет 2 из 5 событий, dropped-count=0. Учитывать вытеснение; обеспечить обнаружение потери terminal events потребителями.

## Code smells

- [x] **F09 — HTTP memory bound.** Размер проверяется после загрузки всего ответа. Читать поток с ограничением байтов и обязательным закрытием, включая redirects и ошибки.
- [x] **F10 — неограниченный chat.** Cached thread pool и очередь не ограничены. Добавить пределы параллелизма/очереди, управляемый отказ и тесты насыщения без зависаний.
- [x] **F11 — состояние и эффекты.** runtime/run! содержит 319 строк, смешивает planning/retries/approval/streaming/fallback; queue смешивает переходы и публикацию. Выделить чистые решения и ограниченные операции исполнения, сохранить поведение.
- [x] **F12 — дублированная shell policy.** Три источника: shell/default-rules, config/defaults.clj, resources/config/default.edn; уже различаются uname. Оставить один канонический источник.
- [x] **F13 — глобальное изменяемое состояние.** loop-states и UI stream maps живут в defonce вне lifecycle. Перенести состояние в экземпляр системы, очистку — в stop; проверить изоляцию двух систем.

## Реализация

- **F01/F12:** каноническая policy в `agent.tools.shell-policy`. `find`, `sort`, `uniq`, `rg`, `git`, `cargo fmt` больше не получают автоматический allow; явные пользовательские правила сохранены.
- **F02/F09:** автоматические redirects транспорта отключены; переходы проверяются вручную. При смене origin остаются только публичные заголовки. Поток читается максимум до limit+1 байта; bodies закрываются также на redirects и ошибках. Проверено mock-потоком и настоящим локальным HTTP redirect.
- **F03/F04:** отменённый worker удерживает сессию до завершения; streaming проверяет request-id. Ошибки уведомлений изолированы; отказ executor завершает ожидающие promises и очищает очередь.
- **F05:** persistence subscriber обязательный; ошибка возвращается вызывающему коду, без успешного финала и повторного provider fallback.
- **F06:** обновление статуса и его чтение выполняются в транзакции. Audit после applied находится за границей rollback файла; проверяется фактически установленный статус.
- **F07:** stdout/stderr дочитываются с отбрасыванием избытка; результат содержит `stdout-truncated?`/`stderr-truncated?`. Общий deadline ограничивает ожидание процесса и readers.
- **F08:** sliding/dropping buffers считают потери и помечают события `:broker/dropped-count`. SSE обнаруживает gap; Telegram завершает ответ по результату задачи даже при потере terminal event, без повторного approval-текста.
- **F10:** bounded executor и ограничения очередей; overload отображается в HTTP 429. Настройки `:chat`: `:max-concurrent-turns` 16, `:max-active-sessions` 64, `:max-queued-per-session` 32, `:max-pending-turns` 256. Отдельный executor для loop workers предотвращает ожидание turns в собственном пуле; отказ запуска убирает активное loop-состояние. Executor сохраняет dynamic bindings.
- **F11:** чистые переходы очереди вынесены в `agent.chat.queue-state`, решения runtime — в `agent.runtime.turn-policy`; planning и recovery выделены из `run!`. Это ограниченный рефакторинг проверенных ветвей, не полная перепись runtime.
- **F13:** loop/UI-состояние принадлежит экземпляру системы; остановка очищает состояние и закрывает UI streams. Проверена изоляция двух экземпляров.

## Границы проверки

Локальные тесты и fault injection подтверждают перечисленные сценарии. Production, настоящий Telegram, браузер и длительная нагрузка не проверялись. Пользовательские shell rules автоматически не переписываются. Изменение file+SQLite не является распределённой crash-safe транзакцией; F06 исправляет воспроизведённый rollback после ошибки audit.
